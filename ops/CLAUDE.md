## 系統不變量

任何改動都不得違反。違反 = bug,不是「新行為」。
由 `tests/test_invariants.py` 逐條驗證。

### 訊號

- 現金 = `max(趨勢腿, VIX腿)`,值域恆在 `[0, 1]`
- 輸出只能落在階梯值上:`{0, 0.24, 0.30, 0.42, 0.60, 0.66, 0.90, 1.00}`。
  出現中間值代表某處做了不該有的內插或平滑
- 兩腿階梯的門檻方向**不同**,這是刻意的:
  - **趨勢腿**(嚴格小於):`mom<0 → 0.30`、`<-0.03 → 0.60`、`<-0.08 → 0.90`、`<-0.13 → 1.00`
  - **VIX 腿**(嚴格大於):`risk>0.5 → 0.24`、`>1.0 → 0.42`、`>1.8 → 0.66`、`>2.6 → 0.90`、`>3.4 → 1.00`
  - 門檻值本身屬於**低**的那一階(例如 `mom = -0.03` 仍是 0.30、`risk = 0.5` 仍是 0)
- 單調性:乖離越低現金不得下降;風險分數越高現金不得下降

### 風險分數

```
risk = 0.55·max(lvl,0) + 0.30·max(z36,0) + 0.15·max(spike,0)

lvl   = (vix_close - 16) / 9
z36   = 36 個月滾動 z-score,【樣本】標準差 ddof=1;前 35 個月取 0
spike = (當月 VIX 日內最高 - 近 6 個月月收均值) / 12;前 5 個月取 0
```

- **`ddof=1` 是不變量。** 母體標準差(ddof=0)會讓 z 系統性偏大,VIX 腿在門檻附近
  多拉現金。Pine 內建的 `ta.stdev()` 正是母體版,所以 Pine 那一份必須手算
- **暖機期補 0 而非 NaN**(對齊 JS)。spike 必須「整式補 0」,不能只把滾動均值補 0 ——
  否則會變成 `(high-0)/12`,是完全不同的數
- `mom_cash(NaN) == 0.0`、`vix_cash(NaN) == 0.0`,對齊 JS 的 `NaN < 0 === false`。
  這是陷阱,已用測試釘住 —— 別「順手修好」它

### 無前視

- 訊號於月收盤確認,執行於次月:`position(t) = signal(t-1)`
- **`shift(1)` 只允許出現在 `backtest.py`**。`engine.py` 只產生訊號,
  PWA 顯示的是當月即時建議而非回測部位 —— 兩者混在一起會讓 parity 測試
  因為設計本身差一個月而永遠紅燈
- 截斷未來資料不得改變過去的訊號(`test_engine_has_no_lookahead`)

## 資料定義(2026-08 定案,全部經實測)

### 價格 = 月收盤

S&P 月收盤 = 該月最後一個交易日的收盤價,由 Yahoo `^GSPC` 日K 聚合。

⚠ **Shiller 資料集的 `SP500` 欄是「當月每日收盤的平均價」,不是月收盤。**
與 Yahoo 月均價實測差異精確為 `0.00`。兩種定義在 **17.3%** 的月份給出不同的
現金建議,乖離率最大差 **10.19 個百分點**。

改用月收盤的理由:它是唯一能成交的價格,也是 12 月均線趨勢濾網的標準構造。
用月均價回測會因為平滑而系統性低估真實回撤。

Shiller 仍保留兩個用途:取股息(算總報酬)、以及 PWA 的最終保底來源。
PWA 退回 Shiller 時會顯示警示列說明定義不同,**不得無聲切換**。

### VIX 月內最高 = 日內最高(HIGH)

不是「當月最高收盤」。2024-08 那次 VIX 盤中衝到 **65.73**,但當月最高收盤只有
**38.57** —— 用收盤會整個漏掉那次事件。歷史上有 **9 個月份**因此翻轉現金水位。

## 體制層(主體判定 + 早期警訊)—— 2026-08-12 新增

`src/regime.py`(純函式)+ `src/fetch_signals.py`(唯一的網路端)+ PWA 的
`#regimepanel`。每日 workflow 產出 `data/signals.json` 推到 `ops-data`,PWA 讀它。

### 最重要的一條:這層不得參與現金水位計算

```
cash = max(mom_cash, vix_cash)          ← 440 個月凍結基準釘住,不准動
早期警訊 = 平行的第二個讀數              ← 只報事實與門檻
```

把新訊號併進 `cash` 會同時毀掉兩件事:**黃金基準**(判斷「有沒有改壞」的唯一依據)
與**驗證能力本身**。而且 CNN 端點只給 **250 天**歷史 —— 用 250 天的雜訊去改一個
用 440 個月驗過的規則,方向就是錯的。

這條由三個測試從三個角度釘住,不是靠自律:

| 測試 | 釘住什麼 |
|---|---|
| `test_regime_does_not_touch_the_engine` | AST 掃描:`regime.py` 沒有 import engine、沒呼叫 `mom_cash`/`vix_cash` |
| `test_pwa_regime_layer_does_not_touch_the_cash_number` | `renderRegime()` 沒碰任何核心讀數的 DOM 節點 |
| `test_core_ladder_constants_are_untouched` | 兩腿階梯的原始字串當金絲雀 |

用 AST 而不是字串搜尋是刻意的:模組 docstring 裡本來就要寫「為什麼不能碰
mom_cash」,字串比對會把那段說明本身判成違規,逼人刪掉最該留的註解。

### 主體判定的定義

對每一對(跟隨者 f、領先者 l)算 `R²(f 今日報酬 ~ l 前一交易日報酬)`,
每個市場當領先者時的 R² 加總 = 領先總分。最高者即金融主體。

- **錯開一天**才有方向性。同日相關分不出誰帶誰。
- 「前一交易日」是 leader 序列中早於 follower 當日的**最近一筆**,
  不是「日期減一」—— 兩地假期不同,硬減一天會大量落空。已用測試釘住。
- **這個定義會失效**,這是它的優點:哪天美國不再帶動全球,分數會自己掉下來。
  一個永遠回答「美國」的硬編碼是信仰不是量測。
- 2026-08-12 實測(近兩年,6 個市場):美國 0.763、歐洲 0.159、香港 0.050、
  日本 0.038、台灣 0.028、中國 0.021。美國那一列(當跟隨者)全部 ≤0.021 ——
  **沒有任何市場帶得動美國**。

### 六條早期警訊

⚠ **門檻沒有經過回測,而且短期內也做不到** —— CNN 端點只回 250 天,
統計顯著性做不出來。它們是常識性的極端值,不是最佳化參數。
**UI 上必須照實說**(`#regimenote` 已寫死這段警語,不得刪)。

意圖:兩腿都要等 VIX 跳、等均線跌破才會動,處理「崩盤中」很好,處理「崩盤前」
**按定義做不到**。這六條看的是「價格還在高檔、但內部已經在惡化」。

- **「缺資料」與「沒觸發」必須在畫面上長得不一樣**(`ok=False` vs `triggered=False`)。
  混在一起的話,資料源死掉會偽裝成一切平安 —— 那正是這整個專案在防的事。
- 信用那條看**變化**不看**水位**:低檔盤整是常態,轉折才是資訊。

### 刻意不做的事

- **不進 `health_check.py`。** 這層是輔助讀數,不該有能力讓每日健檢變紅燈、
  開 Issue。CNN 今天抽風不是「系統壞了」。過期由 PWA 自己在面板上標資料年齡。
  這是「一年只該叫你幾次」的直接後果 —— 多一個會叫的東西,就少一分會被理會的機會。
- **workflow 那步掛 `continue-on-error: true`**,同上。
- **`signals.json` 不留在 `main`**(`.gitignore`),否則會是一份永遠停在某次執行的假現況。

### PWA 那一段的不變量

- **失敗即靜默**:抓不到就整塊 `display:none`。與心跳指示器同一條紀律,
  已用 `test_regime_fetch_failure_is_silent` 釘住 catch 必須是空的。
- **外部字串一律 `esc()`**:`signals.json` 帶有外部來源的值(國發會燈號、
  錯誤訊息),直接進 `innerHTML` 等於把被入侵的資料源變成 XSS 入口。
  對應四道防線的第 4 條。
- **路徑由測試綁死**:`OPS_SIGNALS` 必須等於 `fetch_signals.SIGNALS_PATH`
  相對 repo root 的路徑,且必須指向 `ops-data` 分支。心跳就踩過這個坑
  (寫成 `data/manifest.json`,實際是 `ops/data/manifest.json`),
  而路徑錯在「失敗即靜默」的設計下**完全沒有症狀**。

## 黃金基準

錨定的是 `tests/fixtures/` 的**凍結快照**,不是即時資料 —— 用即時資料當錨的話
每個月數字都會變,測試要嘛天天紅燈、要嘛容差開到失去意義。
更新快照是一個需要人工審視的動作。

### 第一層 · 訊號錨(硬,零假設,精確比對)

窗口 `1990-01 .. 2026-08`,共 **440 個月**。

關鍵時點:`2008-10 = 100%`、`2015-08 = 66%`、`2020-03 = 100%`、`2022-06 = 100%`

水位分布:`0%` 261 月 · `24%` 61 · `30%` 20 · `42%` 23 · `60%` 32 · `66%` 5 ·
`90%` 21 · `100%` 17。水位變動 **158** 次。

### 第二層 · 績效錨(軟,容差 0.5pp)

假設:**總報酬(Shiller 股息)+ 現金收益 0% + shift(1)**,窗口 `1990-01 .. 2023-06`
(切在股息完整的最後一個月)。

| | CAGR | MaxDD | Calmar |
|---|---|---|---|
| 策略 | 8.44% | -25.09% | 0.337 |
| 買進持有 | 10.31% | -50.96% | 0.202 |

⚠ **這個工具是用報酬換回撤,不是兩者兼得。** 測試刻意**不**驗證「報酬要比買進持有高」——
寫成那樣會是個假的、遲早要被放寬的測試。只驗證回撤必須更小。

⚠ 已知事實:在 **OOS 2011-2023** 窗口,策略 Calmar 落後買進持有(0.435 vs 0.528,
且在 0%/2%/4% 三種現金收益假設下都成立)。全期優勢(0.337 vs 0.202)由
2000-2002 與 2008 兩段主導。PWA 上原本宣稱的「OOS Calmar 1.25 > 0.75」來自
舊的月均價定義,已移除。

### Pine 的驗證分兩段,不要混為一談

**第一段 · 邏輯層(已自動化,CI 每次跑)**
`tests/pine_sim.py` 從 `.pine` **原始檔解析**常數與階梯門檻,再用 Pine 的語義
(`ta.sma` 視窗含 na 回傳 na、序列往回索引、樣本標準差手算、`na < 0` 為 false)
重現計算,與 `engine.py` 逐月比對。**測的是那個檔案本身**,不是另抄的副本 ——
改動 `.pine` 裡任何一個數字都會被抓到(已用 6 種突變驗證測試確實會失敗)。

也涵蓋「圖表歷史比 VIX 長」的 na 對齊情境(SPX 從 1988、VIX 從 1990)。

**第二段 · 執行層(必須人工)—— 2026-08-12 部分完成**

邏輯對不代表 Pine 跑得起來。三個只有真的在 TradingView 上跑過才知道的問題:

| # | 問題 | 狀態 |
|---|---|---|
| 1 | `.pine` 編譯得過嗎(語法、型別、版本差異) | ✅ **已驗證** |
| 2 | `request.security` 的行為如假設嗎 | ✅ **已驗證**(見下,不是時序落後) |
| 3 | TradingView 的 VIX/SPX 資料與 Yahoo/GitHub 一致嗎 | ⚠ **已量測:SPX 一致、VIX 不一致** |

### 逐月對帳結果(1990-02 .. 2026-08,439 個月)

匯出 `SP:SPX` 月線全段(1871 起 1673 列)跑 `check_pine_parity.py`:

| 比對項 | 結果 |
|---|---|
| **SPX 月收盤** | ✅ 中位相對差 `3.0e-08`,只有 5 個月 > 0.1% |
| **趨勢動能腿** | ✅ **439/440 一致** |
| **VIX 領先腿** | ❌ **142/440 不一致(32%)** |
| 合計現金水位 | 97/439 不一致 |

**結論:邏輯是對的,差異來自 VIX 資料源。** 三個證據:

1. **不是時序落後。** 把 Pine 整體位移 ±1、±2 個月重算吻合數:
   `-1` → 350/439、`0` → 342/439、`+1` → 266/438。位移 −1 只比不位移好一點點,
   遠不是「對齊後就全中」的樣子 —— 系統性落後會讓某個位移接近滿分。
   (一開始我從兩個資料點猜是落後一個月,**猜錯了**,是逐月統計推翻的。)
2. **不對稱性不存在。** Pine 較高 70 個月、engine 較高 72 個月 —— 隨機分布,
   不是縮放錯誤或單向偏誤。
3. **差異集中在階梯門檻附近。** 不吻合月份距最近 VIX 門檻中位數 `0.154`,
   吻合月份 `0.427`(2.8 倍)。且 110/142 只差**一階**。

也就是:兩家 VIX 供應商的數值只差一點點,但 VIX 腿是**階梯**函式,
門檻附近對輸入極度敏感,一點點差異就翻階。

⚠ **但不能全部推給門檻敏感** —— 有 27 個月差 2 階、5 個月差 3 階,
那超出微小差異能解釋的範圍。**`CBOE:VIX` 與 GitHub `finance-vix` 在某些月份
是真的不同的序列**(最可能是月內最高 `high`,它驅動 spike 項)。

**同一個機制也解釋了趨勢腿唯一那次不吻合:** 1994-12 TradingView 收盤 `461.17`
vs Yahoo `459.27`(差 0.41%),而該月乖離是 `-0.30%` —— 剛好跨過 0 門檻。

### 這代表什麼(以及不代表什麼)

- **PWA 與 `engine.py` 不受影響。** 它們自始至終用同一份 GitHub `finance-vix`,
  內部一致。黃金基準也是錨在那份快照上。
- **TradingView 上的 Pine 指標會與 PWA 顯示不同的水位**,約三分之一的月份差一階。
  這是**已知且已量測**的限制,不是 bug,**不要為了讓它「對上」而放寬容差或改門檻**。
- 想讓兩邊一致,唯一正確的做法是**讓兩邊吃同一份 VIX 資料**,不是調參。

## 自動化架構與安全邊界

```
L1 健檢偵測到異常
      ↓  輸入是我們自己產生且已淨化的報告,不是外人可控的文字
   Claude 診斷 + 修復(autofix job)
      ↓  只能推 fix/ 分支
   開 PR
      ↓
   L2 CI 把關
      ↓
   人按合併  ← 刻意留給人
```

### 為什麼不從 Issue 觸發

2026-06-01 公開的攻擊鏈:在公開 repo 開一個惡意 Issue → `claude-code-action`
讀它 → 交出 repo 寫入憑證。更早在 2 月,Cline 的 triage workflow 被注入在
**Issue 標題**裡的 prompt 偷走 npm token,推了惡意版本,8 小時內裝進約 4000 台機器。

本 repo 條件全部命中:`public`、Issues 對外開放、`main` 直接部署到 Pages。
所以 Claude **只由 L1 自己的健檢報告觸發**,外人碰不到入口。

**不要為了方便加上 `issue_comment` 或 `issues: opened` 觸發。** 真要加,
必須嚴格檢查 actor 等於 repo owner,而且要理解那個檢查本身曾經被繞過。

### 四道防線(缺一不可)

1. **`main` 分支保護要求 CI 通過。** 這是承重牆不是裝飾 —— 實測 `GITHUB_TOKEN`
   帶 `contents: write` 推 `main` 會被 `GH006` 擋下。Claude 拿到的就是這個 token。
2. **所有自動流程都不推 `main`。** 心跳與年度報告推 `ops-data` 分支;
   Claude 只推 `fix/` 分支。沒有任何自動流程有碰 `main` 的理由。
3. **action 釘死 SHA**(`c038e4d` = v1.0.186,遠高於修補漏洞的 v1.0.94)。
   **絕不用 `@main` 或 `@v1`** —— 浮動參照正是出事的用法。
4. **外部內容經 `safe_snippet()` 淨化**才進報告。報告會變成 Issue 內文並可能
   餵給 LLM;原樣嵌入等於讓一個被入侵的資料源把指令注入提示裡。

### prompt 裡的硬性禁令

寫進 prompt 而非只靠期待 —— agent 面對「健檢失敗」最省事的修法就是**把閾值放寬**,
那等於把警報關掉:

- 不得放寬健檢閾值來讓檢查通過
- 不得修改 `tests/fixtures/` 的黃金基準(基準漂移代表有東西壞了,改它是湮滅證據)
- 不得修改 `.github/workflows/`、不得推 `main`、不得外洩 secret
- 外部資料源故障不是程式問題,不得為了綠燈動程式碼
- **判斷不了就說不知道** —— 開一個只有說明的 PR,比硬修一個不確定的東西有價值

### 為什麼合併留給人

`main` 直接自動部署到公開的 GitHub Pages,而那是一個會給出投資部位建議的工具。
自動合併等於讓 agent 無人核可地改變線上建議。這個邊界是刻意的。

## 分層與紀律

| 層 | 頻率 | 誰執行 | 你要做的事 |
|---|---|---|---|
| L1 資料健康 | 每日 | GitHub Actions | 無 |
| L2 邏輯一致性 | 每次 push | CI | 無 |
| L3 年度健檢 | 一年一次 | 手動觸發 | 讀報告 15 分鐘 |

**平常完全靜默,只有壞掉才通知。沒消息就是好消息。**

### 兩條不能破的分層規則

1. **L2 必須完全離線可跑**(靠 `tests/fixtures/`)。否則資料源某天抽風會讓 CI 變紅燈,
   你就分不清是「邏輯壞了」還是「Yahoo 今天不舒服」—— L1 的問題污染 L2 的訊號,
   兩層都失去意義。資料源的死活由 L1 負責。

2. **L1 的通知必須去重。** 資料源掛掉是持續性狀態不是單次事件,
   每天開一個新 Issue 等於一年 365 個。必須是:找開放的 `health-fail` Issue →
   有就留言更新 → 沒有才新建 → 恢復時自動關閉。

### ⚠ GitHub Actions 排程會自動停用

排程 workflow 在 repo 靜置後會被 GitHub 自動停用,而「一年碰一次」正是會觸發它的
使用模式。**沒有心跳的話這套系統會在約兩個月後安靜地停掉,而它的設計就是
沒消息等於正常** —— 你不會發現。

**心跳機制:** 每日 job 把 `data/manifest.json` 與 `data/health_log.csv` commit
回去製造 repo 活動(原始 CSV 不進版控,太大)。

**這個機制沒有被驗證過,而且短期內也無法驗證** —— 它的效果要 60 天才看得出來。
已知的不確定點是:`GITHUB_TOKEN` 產生的 bot commit 是否被 GitHub 計為
「repository activity」。有多方回報它**不算**。

因此**偵測**比**預防**重要 —— 預防驗不了,偵測可以:

1. **GitHub 會在停用前寄 email 通知。** 那封信不要當廣告忽略。
2. **PWA 的心跳指示器** —— `index.html` 的 `checkOpsHeartbeat()` 讀
   `ops-data` 上的 `ops/data/manifest.json`,取所有來源 `fetched_at` 的最大值,
   超過 `OPS_STALE_DAYS`(4 天)就顯示 `#opsnote` 琥珀色警告。

   **這段程式碼有兩條不得違反的性質:**

   - **失敗即靜默。** fetch 失敗、非 200、`fetched_at` 解析不出來 —— 一律不顯示。
     離線與網路故障不是「監控死了」的證據。**不要「順手」把 catch 改成顯示錯誤** ——
     一個會亂叫的指示燈幾天後就會被無視,那等於沒有。已用 5 個分支測過
     (3天/9天/離線/404/壞資料)。
   - **門檻不得低於 3 天。** 心跳是每日的,但單次 outage、GitHub 事故、
     workflow 排隊都會製造 1–2 天空窗。4 天離 60 天大限還很遠,不必激進。

   已知限制:**只在使用者打開 PWA 時才檢查**。它是第二條防線,不是取代 email。

3. **若收到那封信,把心跳改用 PAT 推送**:建一個 fine-grained PAT
   (只需 `contents: write`),存成 repo secret,再把 `daily-health.yml` 的
   checkout 步驟改成 `token: ${{ secrets.HEARTBEAT_PAT }}`。真人身分的推送
   一定算活動。

⚠ **不要拿 repo 的 `pushed_at` 當作「bot commit 有算活動」的證據** ——
2026-08-08 試過,bot 的心跳(`02:29:00Z`)被人類 push(`02:30:25Z`)蓋掉,
分辨不出來。要驗必須挑一段確定沒有人類 push 的窗口再比對。

## CI 綠燈證明不了的事

CI 跑在 **Linux + UTF-8** 的 runner 上,使用者跑在 **Windows + cp950**。
前兩個實測到的 bug 都活在這個縫隙裡 —— 都是 CI 全綠、使用者一跑就爆。

第三個(Service Worker)的形狀不同:它不是環境差異,而是**那個檔案從來沒有
任何測試載入過**。140 條測試涵蓋 `engine.py`、`index.html` 的計算、`.pine`、
資料管線、報告層 —— 唯獨 `sw.js` 是一片空白,而它是使用者每一次開啟 PWA
都會經過的第一段程式。

### 終端編碼(2026-08-09)

Windows 的 Python 預設用系統 ANSI 代碼頁寫 stdout。中文印得出來,
但 `✅ ❌ ⚠ ⏭ ✓ ✗ ∈` 會直接 `UnicodeEncodeError` 中斷整支腳本。

當時三個入口全中,而且全是**使用者會手動跑的那三個** ——
包括健檢自動開的 Issue 內文叫他跑的那一行。也就是:偵測到異常 → 開 Issue →
Issue 叫他跑一個在他機器上必定崩潰的指令。

**規則:任何有 `__main__` 的腳本,`main()` 第一行呼叫 `src/console.py` 的
`force_utf8()`。** 由 `tests/test_reporting.py` 自動掃描強制 ——
那條測試是掃描而非列舉,新增的腳本會自動納入。

不要改用 ASCII 符號來迴避,那是遷就工具而不是修問題。

**2026-08-12 放寬判準(第二次踩到同一類問題):** 原本只掃「cp950 印不出的符號」,
於是 `fetch_data.py`(印「列」)與 `compute_golden.py` 兩支通過了測試 ——
因為它們的中文在 cp950 裡**印得出來**。但印出來的是 cp950 位元組,
管線接到 UTF-8 消費端就是亂碼。**不會崩潰,只會安靜地產生垃圾,比崩潰更難發現。**

判準已改成「**有非 ASCII 就要 `force_utf8()`**」,整類問題一次消掉。
另外補了一條測試證明那個掃描抓得到違規者 —— 掃描式測試若沒有這層,
可能只是恆真而沒人察覺。

### health_log 是「每次執行」一列,不是「每天」一列(2026-08-09)

手動觸發、drill、重跑都會讓同一天出現多列。年度報告原本把列數當天數,
實測把兩天的紀錄印成「10 天」,成功率也跟著失真。

**規則:原始 log 維持 append-only 當稽核軌跡,天數一律在讀取時 groupby 彙總。**
不要反過來去改 `append_log()` 讓它一天只留一行 —— 那會丟掉「當天第幾次執行才過」
這個資訊。一天內有任何一次紅,那天就算紅。

### Service Worker 把失敗的回應存進快取(2026-08-12)

線上巡檢時發現的。`sw.js` 的靜態檔分支是**快取優先**,卻對回應狀態碼照單全收:

```js
fetch(req).then((res) => {
  const copy = res.clone();
  caches.open(CACHE).then((c) => c.put(req, copy));   // ← 404 也存
  return res;
})
```

一次 404 被存進去之後,**就算檔案後來真的部署上去了,SW 仍會一直回那個 404**,
直到 `CACHE` 版本號 +1 為止。導覽分支同樣沒檢查 —— 一張 404 頁會變成離線首頁。

觸發條件很現實:Pages 部署過程中資源短暫 404、或新版加了一個舊版沒有的檔案
而使用者剛好在那個空窗期開了頁面。

**症狀是沒有症狀。** 使用者看到某個檔案讀不到,重新整理沒用(SW 攔在網路之前),
而 DevTools 的 Network 分頁顯示 200 —— 因為那個 200 是 SW 回的,不是伺服器回的。

**修法:**`cacheable(res)` 判 `res.status === 200`,兩個分支都用。

⚠ **不要寫成 `res.ok`。** 206 Partial Content 的 `res.ok` 是 `true`,但
`Cache.put()` 收到 206 會拋 `TypeError`,而那個 `.then()` 後面沒有 `.catch` ——
會變成一個沒人看得到的 unhandled rejection。

**新增 `tests/test_sw.py` + `tests/sw_bridge.mjs`。** 橋接器把真的 `sw.js`
載進假的 ServiceWorker 環境(假 Cache API + 假網路),**真的派送 fetch 事件**,
再回答唯一重要的問題:一個 404 打進來之後,快取裡有沒有多一筆。

刻意不用 grep 原始碼 —— 「有沒有寫 `res.ok`」這種檢查,任何一次分支結構
改寫都會讓它失效卻仍然通過。已用 8 種突變驗證(拿掉任一分支的判斷、
改成 `true`、改成 `res.ok`、完全不快取、SHELL 列不存在的檔、跨網域不放行、
版本號倒退),全部抓得到。

### 健檢會把壞掉的來源存下來,蓋掉最後一份好資料(2026-08-13)

`check_sources_reachable()` 原本長這樣:

```python
if len(df) < floor:
    out.append(Result(..., FAIL, f"只回了 {len(df)} 列,低於下限 {floor}"))
else:
    out.append(Result(..., OK, ...))
manifest[name] = fetch_data.save(name, text)   # ← 在 if/else 外面
```

判定「這份資料壞了」之後,**照樣把它落地**。實測:601 列的好檔被 5 列的壞檔
蓋掉,`manifest` 記上 `rows=5` 與全新的 `fetched_at`。於是稽核軌跡與心跳
同時宣稱「剛剛更新成功」,而檢查本身正在說它壞了 —— 兩個訊號互相矛盾,
而看得到的那個(心跳)是錯的那個。

模組開頭第 2 條原則寫的就是「**只檢查、不修復、不改資料**」。

**順帶修掉的第二件事:**來源清單原本寫死成 `["sp_daily", "vix", "shiller"]`,
改成 `sorted(fetch_data.SOURCES)`。加第四個來源時,舊寫法會安靜地不檢查它 ——
和 FRED 死管線同一個形狀。沒訂 `min_rows` 下限的來源現在會直接紅燈,
不會靜靜略過。

### `Infinity` 寫進 signals.json,整塊體制面板無聲消失(2026-08-13)

`dominance()` 在第二名總分為 0 時回 `float("inf")`(「領先到沒有可比性」,
語意是對的)。序列化那一行的守門式是:

```python
"margin": None if dom.margin != dom.margin else round(dom.margin, 2),
```

`x != x` 只擋 NaN。**`inf != inf` 是 `False`**,所以 inf 一路溜到
`json.dumps`,寫出裸的 `Infinity` —— 那不是合法 JSON(RFC 8259 沒有這個
字面值)。瀏覽器的 `JSON.parse` 直接拋,而 `checkRegime()` 的 catch 是空的,
於是**整塊面板消失,症狀和「檔案不存在」一模一樣**。

**為什麼既有測試抓不到:`json.loads` 接受 `Infinity`。**
`test_payload_survives_json_roundtrip` 在 Python 裡來回一趟,永遠綠燈 ——
但真正的消費端是 JS。**用錯的尺量,量得再勤也沒用。**

修法兩層:`jsonable()` 用 `math.isfinite()` 取代 `x != x`(涵蓋 NaN、
±inf),以及 `write_signals()` 加 `allow_nan=False` —— 哪天漏了一條路徑就
直接拋,而不是安靜寫出一份會讓面板消失的檔案。寫不出來時 workflow 沿用
ops-data 上的舊版:**舊資料好過一份會讓面板消失的新資料。**

新測試一律用 `json.loads(..., parse_constant=<拋>)`,並且有一條真的丟給
Node 的 `JSON.parse`。另外 `num()`(國發會的儲存格轉數字)也一併修掉 ——
`float("nan")` / `float("inf")` 都不會拋。

### 偵測器一直是對的,是通知把它藏起來了(2026-10-14)

這一條和前面每一條都不同:**程式沒有壞,偵測也沒有漏,壞的是資訊傳達。**

| 08-21(Issue 開)| ok | ok | **FAIL** | 1 |
| 08-28 | **FAIL** | ok | FAIL | 2 |
| 09-01 | FAIL | ok | ok | 1 |

| 09-30 | FAIL | **FAIL** | FAIL | 3 |
| 10-02 .. 10-13 | FAIL | FAIL | ok | 2 |

**代理鏈連續失效 47 天、VIX 來源停更 22 天** —— 兩個都真正影響使用者看到的數字,
而它們以「第 N 則留言」的形式出現在一個標題還寫著 `健檢異常 · 2026-08-21`
(那個 shiller 早就自己好了)的 52 則討論串裡。

**根因:去重的 key 是「有沒有開放的 `health-fail` Issue」,不是「哪幾項在失敗」。**

`config.yml` 開頭自己寫的:「狼來了比漏報更致命 —— 一旦你開始無視通知,
整層就等於不存在。」**連紅 54 天的 Issue 就是那個狼來了。**

**修法刻意不動「只有一個 Issue」那條不變量**(它是為了避免一年 365 個 Issue,
那條是對的),改的是報告層:

1. **內文每次換成當前報告** —— 原本永遠停在第一天那一份
2. **標題寫出目前在失敗的是什麼** —— 原本只寫第一次失敗的日期
3. **只在失敗集合【變動】時留言**,並明確列出新增/恢復

失敗集合藏在內文的 `<!-- failset: a|b -->` 標記裡,下一次執行讀它來比對。
**刻意不去解析內文的散文** —— 文案改一次解析就無聲壞掉,而它壞掉的症狀是
「永遠判定沒有變動」,也就是這個修法完全失效且沒有症狀。

判斷邏輯在 `health_check.py`(`failset` / `parse_failset` / `issue_title` /
`change_summary` / `issue_plan`),workflow 只負責編排 —— 寫在 heredoc 裡就測不了。
`None`(舊格式 Issue,沒有標記)與 `[]`(上次沒有失敗)**必須分得開**,
混在一起會把現有每一項都說成新增的。已用 7 種突變驗證。

### 第二意見挑出的洞:離線路徑從來沒被走過(2026-10-19)

把交接文件丟給另一個模型審查,它指出 `sw.js` 的 `.catch(() => caches.match(req) || Response.error())`
有 Promise 真值問題 —— `caches.match()` 回的是 Promise,恆為真,`|| Response.error()` 永遠不會生效。

**它的推理完全正確,但程式碼不是那樣寫的。** 實際是
`.catch(() => caches.match(req).then((r) => r || Response.error()))`,有 `.then()`。
**是我在交接文件的表格裡把自己的程式碼抄錯了**,漏掉 `.then()`。

⚠ **這跟這個專案所有其他坑同一個形狀,只是兩端換成了「程式碼」與「我對程式碼的描述」。**
給審閱者一份錯的描述,它再怎麼認真也只會審到一個不存在的 bug ——
**交出去的摘要本身就是一份需要對帳的實作。**

而它底下那句質疑是對的:**離線路徑從來沒有任何測試走過。**

`sw_bridge.mjs` 裡 `makeFetch(0)`(丟 `TypeError("offline")`)這個機制一直都在,
但**沒有一個情境用它** —— 兩個分支的 `.catch(...)` 完全沒被執行過,
而那正是「使用者離線時打開 PWA」唯一會走的路。補上四個情境後抓到兩件事:

**1. 橋接器自己在說謊。** 假的 `addAll` 無條件塞 5 個合成的 200 回應,**從來不呼叫 fetch**。
   所以「install 失敗、快取是空的」根本到不了,新加的測試會看起來綠燈卻什麼都沒測。
   改成真的走網路、且依規格**原子地** reject 之後才量得到東西。

**2. 分支 ② 會把 `undefined` 交給 `respondWith()`。** 條件:離線 + 導覽 + 快取完全空
   (使用者第一次開 PWA 時就離線,或 Pages 部署空窗期 install 失敗 —— 而
   `install` 的 `.catch(() => {})` 會把它無聲吞掉)。兩次 `caches.match` 都 miss,
   就交出 `Promise<undefined>`,而規格說那不是 Response 就直接算網路錯誤。
   分支 ③ 本來就有 `Response.error()` 兜底,② 沒有。使用者看到的結果其實一樣
   (離線又沒快取本來就打不開),但**兩個分支不一致遲早會變成 bug**。

**判準必須是 `resolvedUndefined`,不能只看 `status`** ——
`undefined?.status ?? null` 也是 null,和「SW 放行給網路」長得一模一樣。

**順帶刪掉一段死碼:** 分支 ③ 的 catch 裡再 `caches.match(req)` 一次是沒有意義的 ——
那條分支是快取優先,能走到 `fetch` 就表示外層那次 match 已經 miss。
突變測試把它拿掉後**所有測試行為完全相同**,那不是測試不夠力,
**是兩種寫法真的等價**。等價突變是在告訴你程式碼有冗餘,不是測試有漏。

### 月頻來源不能用天數判新鮮度(2026-10-19)

`shiller: 50`(天)**每個月必然破線一次再自動復原**。證據是 `ops-data` 的
`health_log.csv`(82 天,append-only):

```
08-21 FAIL(最新 2026-07-01)→ 09-01 ok   ⇒ 2026-08 那一列在 08-31~09-01 抵達
09-22 FAIL(最新 2026-08-01)→ 10-02 ok   ⇒ 2026-09 那一列在 10-01~10-02 抵達
```

兩次獨立觀測一致:**觀測月 M 的那一列在 M+1 月的 1–2 號抵達**。
所以那一列在被下一列取代之前,年齡必然走到約 60 天 —— 任何小於 60 的天數門檻
都會週期性誤報。逐日模擬 2026 整年:**舊判準誤報 130 天(每月 11 天),新判準 0 天。**

**這不是放寬閾值,是判準的單位錯了** —— 應該問「該發布的那一期到了沒」,
不是「最後一期過了幾天」。但這個區分**只有在能證明下面兩件事時才站得住腳**:

| 證明 | 測試 |
|---|---|
| 正常發布節奏下一整年逐日都不誤報(含跨年) | `test_monthly_contract_has_no_false_alarms` |
| 來源真的停更時仍然抓得到,而且是在第一次漏期那一刻 | `test_a_stopped_monthly_source_is_caught` |
| 抵達日晚於寬限日就【應該】被抓到(對照組) | `test_a_late_arrival_past_the_grace_day_is_caught` |
| 舊判準在健康資料上真的會誤報(改動的正當性來源) | `test_the_old_day_threshold_really_did_fire_on_healthy_data` |

**偵測速度的對照要誠實講:** 來源若在 2026-09 之後停更,新判準 **11-05** 報警、
舊判準 **10-22** 報警 —— 新的慢 14 天。但 10-22 那天資料其實是**正常的**
(9 月那期 10-02 剛發布,10 月那期要 11 月初才到),舊判準是在**沒有證據時就報警**。
新判準是在「漏了一期」這件事最早**可知**的那一刻報警。

`config.yml` 的 `freshness` 因此改成宣告式契約:每個來源明說自己的 `cadence`,
daily 用 `max_age_days`、monthly 用 `publish_grace_day`。
少了 cadence 欄位的來源會直接紅燈 —— 和 `min_rows` 同一條紀律。

⚠ **PWA 的 `CAL_LAG_GRACE_DAY=6` 與這裡的 `publish_grace_day=5` 是同一個原則的兩個實例**
(新鮮度要依來源自己的頻率判),但**不是同一個數字**,因為量的東西不同:
前者是「日K 聚合成的月份有沒有跟上日曆」,後者是「月頻來源那一期發布了沒」。
不要為了整齊把它們合併成一個常數 —— 那會讓其中一邊失去依據。

### 抓取失敗 ≠ 沒得判斷(2026-10-19)

2026-10-14 那個「上游紅了就 SKIP」太粗。**只要本機還有上一份好資料,
它有多舊仍然判斷得出來** —— 而來源連續死三週時,那個訊號正是重點
(「你手上最新的那份已經 30 天了」)。一律 SKIP 會把它藏起來。

判準因此改成 **`fetch_data.has_local()`** —— 本機有沒有檔案,不是上游有沒有失敗。
有檔案就照常檢查,並在 detail 裡講明「評估的是本機最後一份好資料」。
真的沒檔案才 SKIP(那才是沒得判斷)。

### 持續失敗 ≠ 持續惡化(2026-10-19)

「只在失敗集合變動時留言」修掉了 52 則留言,但留下一個洞:

```
第 1 天  {vix}   VIX 剛開始落後
第 22 天 {vix}   已經停更 22 天
第 60 天 {vix}   這個來源大概不會自己回來了
```

**集合一模一樣,嚴重程度完全不同,而原本一則都不會說。**

補成三類事件:**集合變動 / 嚴重程度跨級 / 太久沒出聲**。
嚴重程度只看「持續了多久」(7 / 30 / 90 天分四級)—— 那是這一層唯一有的、
而且不會自己騙自己的維度。分級刻意粗糙,同 `Warning.band`。

狀態存在 Issue 內文的標記裡:`failsince`(第一次失敗的日期 + **上次已通知的等級**)、
`lastnotice`(上次真的留言是哪天)。

⚠ **等級是存下來的,不是回頭推算的。** 推算需要同時知道「第一次失敗是哪天」
與「上次留言是哪天」,兩個狀態互相依賴就會產生只在特定時序才重現的錯誤 ——
而那種錯誤的症狀是「某次該提醒卻沒提醒」,完全無聲。

⚠ **修好又壞掉要重新起算。** 恢復的項目直接從字典裡消失,它再壞一次就是一次新故障。
否則一個反覆壞掉的來源會被持續時間灌水、誤判成長期故障。

拿真實軌跡(Issue #2 的 60 天)回放:**舊規則 52 則 → 新規則 10 則**,
而且每一則都帶著不同的原因(1 首次 / 3 新增 / 2 恢復 / 4 跨級)。
已用 7 種突變驗證,其中一個是等價突變(見下)。

### DOM 契約:870 行的 index.html,CSS 與 DOM 幾乎沒有測試(2026-10-19)

既有測試都在驗「計算對不對」或「某幾個特定節點有沒有被碰」,
沒有一條在問最基本的那件事:**`$("xxx")` 參照的那個 id,HTML 裡到底有沒有?**

把某個 id 改名,`$()` 回 `null`,`.textContent = ...` 當場拋 TypeError ——
而 `render()` 一拋,**後面所有讀數都不會被畫出來**,畫面停在「讀取資料中…」,
看起來和「抓不到資料」一模一樣,而且重新整理也救不回來。

`tests/test_dom_contract.py` 做四件事:參照的 id 都存在、**沒有重複 id**
(`getElementById` 只回第一個,另一個永遠更新不到 —— 無聲)、核心讀數節點列舉存在、
以及一條證明掃描真的掃得到東西的控制組。

⚠ **這條測試不能取代真實瀏覽器。** 它只回答「id 存在嗎」,
不知道版面有沒有溢出、手機寬度會不會被切掉。不要因為它綠了就以為 UI 驗過了。

### 還在回 HTTP 200 的死鏡像(2026-10-19)

- 回 **9278 列**(完整歷史)

CBOE 多出來的     正好是停更的那 18 個交易日(2026-09-23 .. 2026-10-16)

### 代理這條路已經沒有未來,而正解一直在手上(2026-10-19)

2026-10-14 那一輪的結論是「免費 CORS 代理正在系統性消失」,而當時給出的
唯一出路是**使用者自己去部署一支 Cloudflare Worker**。那個結論是錯的 ——
不是技術上錯,是**它要求使用者去做工作,而那份工作這個 repo 自己就能做**。

事實攤開來看:

| | 誰在跑 | 有 CORS 問題嗎 |
|---|---|---|
| 每日 workflow 抓 Yahoo / CBOE | GitHub runner | **沒有**(server 端) |
| PWA 抓 Yahoo | 使用者瀏覽器 | 有 → 非經代理不可 |

而這個 repo **已經**每天把 `manifest.json` / `signals.json` 推到 `ops-data`,
PWA **已經**在讀它們 —— 因為 `raw.githubusercontent.com` 送
`Access-Control-Allow-Origin: *`(2026-10-19 實測確認)。

**缺的只是「把市場資料也一起發出去」。** 整條代理鏈從第一順位退到第三順位,
而使用者不需要開任何帳號、不需要信任任何第三方、也不會不小心架出一支開放代理。

#### 格式刻意不是新格式

| 發布物 | PWA 用哪支解析 | 改了幾行 |
|---|---|---|
| `pwa/sp_monthly.json` | `spFromYahoo()` | **0** |
| `pwa/vix_daily.csv` | `parseCSV()` + `buildVixMonthly()` | **0** |

`sp_monthly.json` 是 Yahoo chart JSON 的子集,`vix_daily.csv` 是原上游欄位的
子集(只留 `buildVixMonthly` 真的會讀的 DATE / HIGH / CLOSE)。
所以**只有「bytes 從哪裡來」變了,算法一行都沒動** ——
黃金基準與 JS/Python 對帳測試還釘得住同樣的東西。

#### S&P 只發每月最後一個交易日,而這是恆等式不是近似

`spFromYahoo()` 做的事就是「按 UTC 月分組,取每組最後一筆收盤」。
所以只發每月最後一天,它算出來的 `[{ym, price}]` 與拿到全段日K **完全相同**,
而檔案 421 KB → **19 KB**。

這條恆等式兩邊各釘一次:Python 側 `test_month_end_only_is_identical_to_full_daily`,
JS 側 `tests/mirror_bridge.mjs` 在 jsdom 裡跑**真的那支** `spFromYahoo`
並比對兩種輸入的輸出字串。只釘 Python 側不夠 —— 跑在使用者瀏覽器裡的是 JS 那支。

#### 代價寫出來,不要藏

```
sp_monthly.json   19,240 bytes   682 個月(1970-01 .. 2026-10)
vix_daily.csv     80,887 bytes   3,550 列(近 14 年,DATE/HIGH/CLOSE)
```

每天重發一次,約 100 KB/天。VIX 的 14 年是算出來的不是挑的:
畫面上的歷史圖是最後 **96** 個月,每個月的風險分數需要前 **36** 個月的
滾動 z 分數 → 132 個月 = 11 年,14 年留三年餘裕。
要再壓的話唯一的槓桿是按年切檔(`vix_history.csv` 一年才變 +
`vix_recent.csv` 每天變),代價是 PWA 多一次 fetch 與一段串接邏輯。
目前不值得,但數字記在這裡,下次有人嫌 repo 大的時候不用重新量。

### 嚴重程度跟著後果走,和關掉警報只差一個證明(2026-10-19)

鏡像上線之後,「PWA 代理鏈」這一項的語意變了:代理全死但鏡像正常時,
**使用者看到的數字完全正確**。而它從 2026-08-28 起就是紅的。

一個永遠紅著的項目就是狼來了(本檔 2026-10-14 那一節的全部內容)。
但「因為它一直紅所以讓它別紅」是**關掉警報**,是這個專案明文禁止的三件事之一。

界線在哪裡,寫成可執行的:

```
鏡像壞 + 代理全死 → FAIL   ← 這條是安全網
鏡像好 + 代理全死 → SKIP   (不進「異常項目」,但完整留在 details 裡)
代理還活著        → OK     ← 控制組:證明差異來自 mirror_ok 而非探測結果
```

三條都在 `tests/test_proxy_chain.py`。**最重要的是第一條** ——
少了它,「嚴重程度取決於鏡像」就只是「永遠不報警」的另一種寫法。

**放寬閾值 = 把紅線往外挪,讓同一件壞事不再觸發。**
**嚴重程度跟著後果走 = 同一條線,但後果真的變了,而且新的承重點拿到了
自己的、更嚴格的檢查。** 分辨兩者的方法是問:**原本那件壞事,現在還會紅嗎?**
會 → 是後者。不會 → 是前者,你在關警報。

順帶:`SKIP` 在這裡被當成「判準不適用」而不是「判不出來」。
它仍然完整出現在報告的 `<details>` 裡 —— 把「看得到」和「被叫起來」分開,
正是 2026-10-14 那一輪學到的東西。

### 我自己寫的新鮮度檢查,永遠算出 0 天(2026-10-19)

新加的 `check_published_mirror` 這樣寫:

```python
age = _days_between(last, date.today())
if age > mcfg["max_age_days"]:
    ...FAIL
```

看起來完全正確。而 `_days_between` 的簽章是 `(a: str | None, b: str | None)`,
內容是 `date.fromisoformat(b) - date.fromisoformat(a)`,外面包一層
「解析不出來就回 0」。傳一個 `date` 物件進去 → `TypeError` → **被吞掉 → 回 0**
→ `0 > 5` 永遠為假 → **整條新鮮度判準是空轉的。**

抓到它的是我為這個新檢查寫的兩條 age 測試。沒寫那兩條的話,
這個檢查會以「綠燈」的形式存在很久,而它的工作正是偵測另一個會靜默的故障。

根因不是打錯字,是**同一個函式被兩種用途共用**:

| 用途 | 輸入來自 | 「壞的回 0」對不對 |
|---|---|---|
| 通知:這一項壞多久了 | Issue 內文的狀態標記(外部、可被人編輯) | **對** —— 不該讓通知流程掛掉 |
| 量測:鏡像有多舊 | 我們自己剛讀到的資料 | **錯** —— 型別寫錯變成無聲的永遠通過 |

修法是讓它對兩種輸入都真的算得出來(`_as_date` 同時吃 `str` 與 `date`),
不是在呼叫端補 `.isoformat()` —— 後者只修掉今天這一個呼叫點,
下一個人還會踩同一個洞。

**推論:「失敗時回安全值」在通知路徑上是紀律,在量測路徑上是陷阱。**
一個會把錯誤吞成「沒事」的函式,放進判準裡就等於把判準關掉。
共用之前先問:**這兩種用途對「壞掉」的正確反應是同一個嗎?**

### localStorage 用量:從「沒量過的擔心」變成量過的數字(2026-10-19)

`reports` 的 §3.3 從 2026-10 起掛著一個**未驗證**項目:
「localStorage 約 1 MB,iOS Safari 可能爆掉」—— 寫入量估過,
但從來沒有真的量過,也沒有重現過 iOS 的配額失敗。

改用資料鏡像之後順手量了線上版:

```
cwgauge_v2    113,429 chars = 222 KB (UTF-16)
  vt (VIX 原文)      80,887 chars
  spArr              682 筆
```

之前是約 550 KB —— 因為那時 `vt` 存的是上游完整 CSV
(含 OPEN/LOW 兩個從來沒被讀過的欄位,加上六位小數的尾零)。
鏡像只發 `DATE,HIGH,CLOSE` 且數值去尾零,所以快取跟著小了一半以上。

222 KB 距離 iOS Safari 常見的 5 MB 單一來源上限還很遠。
**這個項目可以從「未驗證的擔心」結案了** —— 不是因為它被修好,
而是因為它被量了,而量出來的數字不構成問題。

**推論:一個掛了很久的「可能有問題」項目,最便宜的處理方式通常是去量它。**
猜測會一直留在清單上消耗注意力;一個數字可以讓它結案或升級成真的工作。

### shell 的重導向會在命令失敗【之前】就把檔案清空(2026-10-19)

workflow 第 5 步取回既有的健檢軌跡:

```bash
git show origin/ops-data:ops/data/health_log.csv > ops/data/health_log.csv
```

重導向是 shell 在 fork 之前做的 —— **目的檔在 `git show` 開始執行之前就被
截斷成 0 bytes**。所以那一行只要失敗(分支還不存在、remote-tracking ref 沒建出來、
網路抽風),留下的就是一個**存在但空的**軌跡檔。

接著 `append_log()` 判斷要不要寫表頭:

```python
header = not HEALTH_LOG.exists()     # <- 檔案「存在」,所以判定表頭已經有了
```

於是它直接追加一列資料,整份 CSV 從此沒有表頭。實測下一次 `pd.read_csv`:

```
欄位 = ['2026-10-19', '1', '1.1', 'Unnamed: 3']
列數 = 0
```

**稽核軌跡靜靜變成一張空表**,年度健檢的「資料源穩定度」會說沒有紀錄,
而沒有任何東西會紅 —— 因為每一步都「成功」了。

兩邊各補一道,刻意不共用:

| 層 | 修法 |
|---|---|
| shell | 先寫暫存檔,`[ -s ... ]` 確認非空才 `mv` 過去 —— 不成功就不碰目的檔 |
| Python | `header = not exists() or st_size == 0` —— 判準是**有沒有內容**,不是存不存在 |

Python 那一道留著不是重複:**表頭的正確性是 `append_log()` 自己的責任,
不該依賴呼叫它的那段 shell 寫對。**

### `A && B || C` 不是 if/else(2026-10-19)

心跳步驟原本是:

```bash
git fetch origin ops-data 2>/dev/null   && git checkout -f -B ops-data origin/ops-data   || git checkout -f -B ops-data
```

讀起來像「fetch 成功就 checkout 遠端那條,否則開新的」。實際語意是
**B 失敗時 C 也會跑** —— 而 C 是「從目前的 HEAD(也就是 main)開一條新的
ops-data」,接下來的 `git push` 會是非快轉而被拒。

這不是假想的:`git fetch origin ops-data` 只保證寫 `FETCH_HEAD`,
**remote-tracking ref 要不要順手建出來,取決於 `remote.origin.fetch` 有沒有
涵蓋它** —— 而 `actions/checkout` 會把它縮窄成只有當前分支。

實測(`git clone --depth 1`,refspec 就是 `+refs/heads/main:refs/remotes/origin/main`):

```
舊版:commit 的 parent = main 的 HEAD    -> push 會被拒
新版:commit 的 parent = 7a06d59         -> 真正的 ops-data,快轉成功
```

⚠ **誠實說明:線上那一版一直是好的**(workflow log 裡看得到
`c5d532f..8da2230` 推送成功),所以這是把一個潛在脆弱點拿掉,不是修一個
正在發作的故障。真實 runner 的 refspec 顯然涵蓋得到,但那是**賭別人的預設值**。

改成 `if/else` + 明確 refspec `+refs/heads/ops-data:refs/remotes/origin/ops-data`,
兩種環境都成立。

**推論:workflow 的 shell 沒有測試,所以它要寫成「讀起來就是它的語意」。**
`A && B || C` 在這一點上失格 —— 它讀起來像 if/else,但不是。
而驗證它的方法也不用靠想:**把那段 shell 從 YAML 抽出來,在一個更嚴苛的
環境裡真的跑一次**(我就是這樣發現它的)。

### 能產生出來,不代表它每天真的被產生(2026-10-19)

鏡像那一層寫了 15 條測試,證明 `publish_pwa.py` **跑起來**會寫出對的東西:
恆等式、UTC 分月、欄位子集、兩份各自獨立失敗、空聚合不發布。
**一條都沒有證明它每天真的被跑、順序對、而且推得上去。**

而 `signals.json` 早就有那一條(`test_signals_is_pushed_by_the_daily_workflow`),
理由就寫在旁邊:心跳踩過「路徑錯了但完全沒有症狀」。
鏡像現在是 PWA 的**第一順位來源**,卻是三份發布物中唯一沒有被綁住 workflow 的。

三條鏈各自斷掉的症狀:

| 斷在哪 | 使用者看到什麼 | 什麼時候會紅 |
|---|---|---|
| workflow 沒跑 `publish_pwa.py` | 鏡像凍結在最後一次手動執行那天 | 健檢的「PWA 資料鏡像」滿 5 天 |
| 鏡像那步排到健檢**之前** | 同上,而且**每天**都如此 | 同上 |
| 心跳沒 `git add ops/data/pwa` | 同上 | 同上 |

三種都是 HTTP 200、欄位正確、`spFromYahoo()` 解析成功 —— 正是本檔
「還在回 HTTP 200 的死鏡像」那一節的形狀,只是這次的死因是我們自己。
5 天的年齡門檻是安全網,但它報的是「鏡像舊了」,**說不出「因為它根本沒在跑」**。

順序那一條在本機完全驗不出來:`publish_pwa.py` 讀 `data/raw/*.csv`,
而在乾淨 runner 上那些檔案**只有**可達性檢查抓成功才會落地 ——
本機的 raw 檔一直都在。和 `test_check_order_is_load_bearing` 同一個理由,
只是這次順序寫在 YAML 裡,而 YAML 原本沒有任何測試讀過。

⚠ **這類掃描式測試最容易變成恆真。** `_step_index()` 因此在找不到、
或找到多個時都**硬失敗**:步驟哪天被刪掉,順序比較若只是拿到 `-1`
就會悄悄通過 —— 而那正是最該紅的情況。
(測試解析 YAML 而不是比對字串,也是為了讓「重排」真的被看見。)

刻意只取 `jobs.health.steps`:autofix 那個 job 在**另一台 runner** 上,
檔案系統不共用,鏡像若跑在那裡 `data/raw/*.csv` 根本不存在。

四個突變(M17–M20)逐一反向驗證過,見下表。

### 整個 repo 唯一沒有重試的網路讀取,偏偏是第一順位來源(2026-10-19)

`fetch_data._get()` 從一開始就是 **3 次指數退避**(「任何失敗都值得重試」)。
而當天新加的 `check_published_mirror()` 是一行裸的 `requests.get(...)` ——
整個 repo 唯一沒有重試的網路讀取,而它讀的是 PWA 的**第一順位來源**。

真正的問題是它的失敗會**放大**:

```
鏡像讀取拋例外  →  那一項 FAIL
                →  mirror_is_serving() 回 False
                →  「PWA 代理鏈」從 SKIP 翻回 FAIL(安全網,刻意如此)
                =  一次 20 秒的網路抽風 → 2 項故障 + 改標題 + 留一則言
```

那正是本檔反覆在防的狼來了,而且來源是**我們自己的量測設備**,不是資料。

實測 `ops-data` 上 67 天的 `health_log.csv`:**沒有任何一天出現「隔天就自己
好了」的來源可達性失敗** —— 失敗全都是連續多天的真故障(19 / 16 / 7 / 11 天)。
這不是「網路很穩所以不用重試」的證據,恰恰相反:**那些讀取全都走
`_get()` 的三次重試**,所以暫時性故障從來沒有進到軌跡裡。鏡像是唯一沒有
那層保護的。

#### 重試只給「問不到」,不給「伺服器明確回答了」

| 情況 | 重試 | 理由 |
|---|---|---|
| 連線錯誤 / 逾時 | 是 | **我們沒能問到** —— 這不是鏡像壞了的證據 |
| 5xx | 是 | CDN 自己的暫時性故障 |
| 4xx(含 404) | **否** | 伺服器明確說「沒有這個檔案」,那是定論 |

4xx 不重試是刻意的:把它也塞進重試,只會讓每次健檢多等兩輪退避,
而且會讓「問不到」與「明確沒有」在程式裡糊成同一件事 ——
這份專案在 SKIP/FAIL 的界線上已經反覆踩過這條線。

#### 為什麼這不是放寬閾值

**沒有任何判準移動。** 404 仍然 FAIL、過期仍然 FAIL、格式不符仍然 FAIL、
連續三次讀不到仍然 FAIL(而且代理鏈的安全網豁免會跟著消失)。
改的只有一件事:「問一次」變成「問三次才算問不到」。
用本檔那條分辨法:**原本那件壞事(鏡像真的不見了或凍結了),現在還會紅嗎?
會。**

代價寫出來:最壞情況每個網址多等 `20+20+20` 秒逾時 + `1+2` 秒退避,
兩個網址合計約 **126 秒**。健檢沒有 job timeout,可接受。

五條測試(`test_mirror_check.py`),其中兩條是安全網不是功能:
一次抽風後成功 → OK(且真的問了 2 次)/ 持續讀不到 → **FAIL**
且 `mirror_is_serving` 為 False / 404 **只問一次** / 5xx 重試 / 持續 5xx →
FAIL 且 detail 帶狀態碼。三個突變(`_MIRROR_RETRIES=1`、連 4xx 也重試、
重試用完回一個假的 200)全部被抓到。

#### M2 抓到的是一條空轉的判準

M2 是唯一一個「不是人為設計的突變,而是我原本就寫錯的程式碼」。
突變後的失敗訊息直接印出了那個 bug 的樣子:

```
Result(name='PWA 資料鏡像 · S&P', status='OK',
       detail='200 個月,最後 2026-10-11(0 天前)')
```

一個 8 天前的日期被報成 **0 天前** —— 因為 `date` 物件進了只吃字串的函式,
`TypeError` 被「壞的回 0」吞掉。詳見上面「我自己寫的新鮮度檢查,永遠算出 0 天」。

**突變測試在這裡不是在驗測試,是在驗程式。** 重跑一次就看得到:
把 `_days_between` 的 `date` 支援拿掉,那兩條 age 測試立刻紅,
而紅燈訊息本身就是根因。

#### 怎麼重跑

突變腳本是一次性的(寫在 scratchpad,不進版控)——
它只是對原始碼做字串替換、跑 `pytest tests/ -q -x`、再還原。
要重做的話照上面表格的「突變」欄手動改一行、跑一次、改回來即可。
**刻意不把它做成常駐工具**:一個沒人在跑的突變框架會腐爛成另一個
「宣稱有、實際沒接」的東西,而這份表格本身就是結果的保存形式。

### 等價突變:突變逃掉不一定是測試的問題

這一輪有兩個突變「逃掉」,兩個都**不是測試不夠力**:

| 突變 | 真相 |
|---|---|
| 拿掉分支 ③ catch 裡的 `caches.match(req)` | 那條分支是快取優先,走到 fetch 就代表外層已經 miss ——**那段是死碼** |
| 沒留言時也把嚴重程度等級推上去 | 只要等級上升,`added`/`escalated` 必定非空 → 必定留言,**條件式目前走不到不同分支** |
| 拿掉 CBOE 日期的 `format="%m/%d/%Y"`(2026-10-19) | pandas **2.x** 遇到前後不一致的欄位會直接 raise,不會像 1.x 那樣靜靜改用日在前。實測 `to_datetime(["01/02/1990","13/01/1990"])` → `ValueError`。所以在**目前的 pandas 版本上**兩種寫法等價 |

最後那一筆值得停下來看一眼:它等價的理由是**相依的版本**,不是程式的結構。
`requirements.txt` 給的是範圍不是鎖定,所以「等價」這個結論的有效期
等於「CI 會裝到哪一版 pandas」—— 留著 `format=` 的成本是零,
而它釘住的是跨版本的語意。**等價突變也有保存期限。**

#### 不是等價,是我的測試太弱(同一輪,2026-10-19)

另一個逃掉的突變是「`publish_pwa` 改用本地時區分月」。我一開始判它等價 ——
錯了。它逃掉是因為**我餵的輸入分不出來**:

```
輸入 ["2026-01-30"]                   utc=True 與不給 utc  → 完全相同
輸入 ["2026-02-01T07:00:00+08:00"]    utc=True → 2026-01   不給 utc → 2026-02
```

純日期字串在兩種解析下的日曆日與 epoch 都一樣(pandas 對 naive Timestamp
的 `.timestamp()` 本來就當 UTC)。換成帶時間與偏移的輸入,突變立刻被抓到。

**分辨方法:等價突變在「任何輸入」下都給同樣的結果;弱測試只是在
「我挑的那個輸入」下給同樣的結果。** 判成等價之前,先試著造一個會分岔的輸入 ——
造不出來才是等價。

第一個的正確反應是**刪掉冗餘**;第二個是**留著並註明它釘的是語意不是現況**
(哪天 speak 多了一條抑制條件,沒有它就會出現無聲漏報)。

**突變逃掉時要先問「是測試弱,還是這兩種寫法真的等價」** —— 把等價突變當成
測試漏洞去補,只會長出一條永遠為真的測試。

### 推論

**只在 CI 上跑過的東西,等於只在一種作業系統上驗過。** 凡是文件叫使用者
在本機執行的指令,都要真的在 Windows 上跑一次再寫進文件。

**沒有測試載入過的檔案,不管它多短,都算沒驗過。** `sw.js` 只有 56 行、
邏輯「顯而易見」,所以三輪 debug 都跳過了它 —— 而它是使用者每次開啟
PWA 的第一段程式。短不等於對。

**用消費端的尺量,不要用產生端的尺。** Python 的 json 比 JS 寬鬆,
Python 的 `float()` 接受 `"inf"`,Windows 的 stdout 比 Linux 窄。
每一次踩到的坑都在同一個位置:**兩端對同一份東西的定義不一樣,
而測試只站在其中一端。**

**量測本身也會站錯環境。** 2026-10-14 連續踩到兩次:
「文件的指令在我這台機器上跑得起來」(本機早就手動裝了那個套件)、
「報告裡沒有絕對路徑」(那條路徑在那個情境根本沒被走到,測試是恆真的)。
**判準要測在事實產生的地方,而且要在它真的會發生的環境裡測。**

**偵測對了不等於有人知道。** 前八個坑都是「偵測漏了」,第九個不是:
健檢每天都正確地報告了事實,而使用者 47 天不知道工具已經劣化 ——
因為去重的 key 是「有沒有開放的 Issue」,新故障於是變成 52 則留言中的一則,
標題還凍結在早就恢復了的第一個原因。
**一條永遠紅著的警報,和沒有警報是同一件事。**
下次設計任何通知時先問:**狀態變了,它看得出來嗎?**

**交出去的摘要本身就是一份需要對帳的實作。** 2026-10-19 把交接文件送去
第二意見審查,它根據我抄錯的那一行程式碼,認真地審出一個不存在的 bug。
推理完全正確,輸入是錯的。**描述與程式碼也是「兩端」** ——
同一個形狀,只是這次兩端是「我寫的東西」和「我說我寫了什麼」。

**判準要依被量測對象自己的節奏定義,不是挑一個看起來合理的數字。**
月頻來源配日數門檻,必然每個月誤報一次(實測一年 130 天)。
「改判準的單位」和「放寬閾值」的界線是:**前者要能證明在健康資料上不再誤報、
而且對真故障的偵測沒有變弱**,後者證明不了。拿不出那兩個證明就是在關警報。

**突變逃掉時先問是測試弱還是兩種寫法等價。** 把等價突變當成測試漏洞去補,
只會長出一條永遠為真的測試 —— 那比沒有測試更糟,因為它看起來在把關。

**「可達性」量的是伺服器還活著,不是資料還活著。** 一個凍結的鏡像在
HTTP 狀態、列數、欄位、編碼上全部正常 —— 只有「內容有沒有前進」看得出來。
加任何新來源時都要問:**它死掉的時候,哪一項檢查會變色?**
答案是「只有新鮮度」的話,新鮮度就是承重牆,不准動它。

**要求使用者去做的工作,先問這個 repo 自己能不能做。** 代理鏈死掉之後,
2026-10-14 給的出路是「請使用者部署一支 Cloudflare Worker」。那不是解法,
是把問題轉嫁出去,而且附帶一個會變成開放代理的風險。
正解是每日 workflow 自己發布資料 —— 能力一直都在手上,只是沒看見。
**先盤點「我們已經有什麼」,再去設計「使用者還要做什麼」。**

**嚴重程度跟著後果走,和關掉警報,只差一個證明。** 分辨方法是問:
**原本那件壞事,現在還會紅嗎?** 會 → 是前者(而且那條路徑要有測試)。
不會 → 是後者,你在關警報。

**「失敗時回安全值」在通知路徑上是紀律,在量測路徑上是陷阱。**
`_days_between` 把解析失敗吞成 0,對讀 Issue 標記是對的,
對算資料年齡是**把判準整條關掉**。共用一個函式之前先問:
**這兩種用途對「壞掉」的正確反應,是同一個嗎?**

> 同一個陷阱在同一輪踩了**兩次**。第一次是傳錯型別(`date` 進了只吃字串的
> 函式);第二次是 VIX 鏡像那一邊沒有檢查「最後一筆真的是日期」——
> 一份 DATE 欄全是垃圾但有 132 個不同前七碼的檔案,會得到 age=0 而被判 OK。
> S&P 那一邊靠 `_mirror_last_day()` 回 None 早就擋住了,VIX 那邊少了對應的一道。
> **兩個分支做同一件事卻只有一個有護欄,是「寫兩次」必然會長出來的東西。**

**環境符不符合宣告,本身就需要一條測試。** 這是第三次踩同一個形狀了
(cp950、pytest-cov、pytest major)。前兩次都只補了那一個洞;
真正的修法是讓「執行環境 ≠ requirements.txt」變成一條會紅的測試。
**沒有被檢查的宣告,就只是註解。**

**等價突變也有保存期限。** 一個突變之所以等價,有時是因為相依套件
目前的行為(pandas 2.x 對日期格式不一致會 raise,1.x 會靜靜猜),
不是因為程式的結構。而 `requirements.txt` 給的是範圍不是鎖定。
**判「等價」時要連同它成立的前提一起寫下來。**

**判成等價之前,先試著造一個會分岔的輸入。** 等價突變在**任何**輸入下
都給同樣結果;弱測試只是在**我挑的那個**輸入下給同樣結果。
造不出分岔的輸入,才是等價 —— 這一輪我把一個弱測試誤判成等價,
換成帶時區的輸入之後突變立刻被抓到。

**自己三十分鐘前放的地雷也是地雷。** scratchpad 裡一個叫 `inspect.py` 的
臨時腳本,讓乾淨 venv 裡的 numpy 匯入直接炸掉 —— 解釋器會從當前目錄載入。
環境說明明文警告過這件事,我還是踩了,因為「那是我自己寫的檔案」。

**當一個 bug 的修法只有一行時,先問「為什麼沒有測試抓到它」。**
那一行是症狀,沒有測試才是病。鏡像層那個 `if(!worker && !key)` 刪掉只要三秒,
但真正的問題是整條來源退回鏈從來沒有任何測試走過 —— 它碰網路,所以歷來被跳過,
而它是唯一決定「使用者看到的數字來自哪裡」的地方。

**順序本身就是契約,就要斷言順序。** 只斷言「最後選了誰」的話,
「跳過某一層直接命中下一層」和「照順序試下來」是分不開的 ——
而前者正是這次的 bug。退回鏈的測試要連**實際發出的請求順序**一起斷言。

**一個掛了很久的「可能有問題」項目,最便宜的處理方式通常是去量它。**
localStorage 的配額擔心掛了兩輪沒人動,實際量只花三十秒:222 KB,
距離 iOS Safari 的 5 MB 上限很遠,結案。
猜測會一直留在清單上消耗注意力;一個數字可以讓它結案或升級成真的工作。

**能產生出來,不代表它每天真的被產生。** 一份發布物需要三條各自獨立的綁定:
**有人呼叫它**、**順序對**、**推得上去**。`publish_pwa.py` 的 15 條測試把
「寫出來的東西對不對」釘得很死,三條綁定一條都沒有 —— 而三者斷掉的症狀
完全相同:鏡像凍結,HTTP 200,畫面正常。加任何發布物時要問:
**它如果今天起不再更新,哪一項檢查會變色,而那一項說得出原因嗎?**

**「我們問不到」和「它壞了」在量測路徑上必須分得開。** 這和 SKIP/FAIL
是同一條線,只是搬到了網路層:一次抽風不是鏡像死掉的證據,而重試是唯一
不移動任何判準就能把那個假訊號消掉的辦法。而重試的安全網要自己有測試 ——
「重試」與「永遠不報警」在程式上只差一個 `raise`。
**順帶一條檢查法:列出所有網路讀取,問哪幾個沒有重試。**
這個 repo 的答案曾經是「只有那個看著第一順位來源的」。

## 改動後要做什麼

改 `engine.py`、`index.html` 的計算邏輯、或 Pine → 跑:

```bash
cd ops && python -m pytest tests/ -q
```

改 `index.html` 的**任何**內容 → 把 `sw.js` 的 `CACHE = "cwgauge-vN"` 版本號 +1。

反過來單獨 +1(沒動 `index.html`)是安全的,效果是強制清一次所有使用者的快取 ——
修掉快取污染類的問題時就該這樣做,否則舊的壞條目會留在使用者機器上。

黃金基準真的該變時(例如刻意改了策略)→ 重新產生 `tests/fixtures/golden_*`,
並在 commit 訊息裡寫清楚**為什麼**數字該變。基準漂移若沒有理由,那就是 bug。
